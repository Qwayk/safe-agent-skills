# Wix

**Capability:** Reads + careful changes

Wix work should start by confirming the site, app instance, scopes, and change family before anything live is touched. The agent can review account, site, contributor, app, product, event, CRM, booking, and other Wix API areas, then prepare reviewed plans for changes.

Why this exact service matters: Wix combines site, account, business app, and customer data APIs, so the safest first move is to prove the site context before planning a change.

A good first ask is: “Check the Wix setup, show me what is connected, and suggest the safest next action before I allow live changes.”

## What access this skill needs

- App-token path (site-level families): `WIX_APP_ID`, `WIX_APP_SECRET`, and `WIX_INSTANCE_ID` in your local `.env` file.
- Optional manual fallback: `WIX_ACCESS_TOKEN`.

## How this skill stays safe

- Safe checks do not change anything.
- Writes follow a plan-first workflow: dry-run, review, then explicit confirmation.
- Batch writes and higher-risk actions need stronger confirmation and explicit approvals.
- The tool keeps receipts and run history so you can review what happened.
- No hidden rollback is promised.

## What happens before live changes

- The tool should show dry-run output first.
- You should review risk, app scope, target identifiers, and the saved plan before live apply.
- Live Wix writes in the risky families use a reviewed-plan flow: create the plan with `--plan-out`, then rerun that saved plan with `--plan-in --apply --yes`.
- Additional approvals are required for irreversible or no-snapshot paths.
- Live applies should leave receipts only after successful execution.

## What proof it leaves behind

- Plans are saved as JSON with `--plan-out`.
- Receipts are saved with `--receipt-out` on apply.
- `.state/runs/` stores local run metadata for later review.
- Docs, tests, proof files, and coverage docs are kept in this repository.
- App Permission commands are shipped in this boundary with explicit auth/path caveats; they are implemented but live-unverified until Wix official auth and docs wording are fully aligned.

## Limits

- The official Wix boundary is accounted in `docs/api_coverage.md`: callable families are implemented with explicit named commands, and non-command surfaces are marked gated, callback-only, developer-preview, deprecated, docs-only, site-defined, or disabled.
- Do not publish this tool publicly without Shai's separate release approval.
- Many families remain live-unverified against real Wix accounts, especially contract-gated, beta-gated, and side-effect-heavy methods.
- GraphQL, raw REST, SDK pass-through, generic async-job runner, and call-anything bridges are intentionally not exposed.
- Callback, webhook, service-plugin, recipe-only, and site-defined surfaces are documented but not exposed as normal CLI commands.
- Notifications are still limited to `notifications notify` only; delivery reporting is provider-response-only and no end-to-end delivery proof is currently exposed.

- `site-folders update` is intentionally narrow: it only renames a folder.
- `locations archive` is an irreversible write path and requires `--ack-irreversible` with `--apply --yes` and plan-first.
- `locations update` is full-object replace style and verifies success with read-back by location ID.
- `tags create`, `tags update`, and `tags delete` now use the same plan-first write shape. `tags delete` also requires `--ack-irreversible`, and the receipt stays honest about manual-only recovery.
- `site-properties` writes are plan-first and `--apply --yes`; `update-business-schedule` replaces the `businessSchedule` section and can overwrite values if callers pass incomplete payload.
- `site-urls` methods are read-only in this boundary and do not send any write flags.
- `notifications notify` is a write with explicit plan-first flow in this boundary (`--plan-out`, then `--plan-in --apply --yes`). It requires Wix app or Wix user identity auth for the current site context, needs `--notification-template-id`, expects `dynamicValues` mappings in `"{ placeholder: { text: \"value\" } }` format, and requires `Manage Notifications` (`SCOPE.DC-NOTIFICATIONS.MANAGE-NOTIFICATIONS`). Official provider docs currently note a `100,000` calls/month per-site limit.
- `notifications notify` is live-unverified here because the command only has provider-response proof (`notificationBatchId`) and does not expose end-to-end delivery verification.
- `multilingual-locale-settings` ships the official Wix Multilingual Locale Settings methods: `get`, `set-mode`, and `update`. Writes are dry-run first; applying `set-mode --enabled false` requires `--ack-irreversible` because disabling multilingual mode removes translated content and resets locale settings.
- `multilingual-locales` ships the official Wix Multilingual Locales methods for creating, reading, updating, deleting, querying, bulk-changing locales, changing the primary locale, checking primary-locale change status, listing supported locales, and setting the visitor primary locale. Locale deletes and primary-locale changes require `--ack-irreversible`.
- `multilingual-translation-schemas` ships the official Wix Multilingual Translation Schema methods for creating, reading, updating, deleting, querying, listing site schemas, and getting schemas by key. Writes are dry-run first; schema deletes and updates that remove fields require `--ack-irreversible`.
- `multilingual-translation-contents` ships the official Wix Multilingual Translation Content methods for creating, reading, updating, deleting, querying, searching, bulk-changing content, and updating content by schema/entity/locale key. Writes are dry-run first; deletes, bulk deletes, and updates that remove fields require `--ack-irreversible`.
- `multilingual-translation-published-contents` ships the official Wix Multilingual Translation Published Content query method as a read-only command. The command requires the official schema-key filters and keeps published-content events callback-only.
- `multilingual-machine-translation` ships the official Wix Multilingual Machine Translation methods for translating one content unit or up to 1,000 units in bulk. Translation calls are dry-run first and require `--ack-irreversible` for live apply because successful requests spend word credits.
- `multilingual-machine-translation-credit-data` ships the official Wix Multilingual Machine Translation Credit Data methods as read/helper commands for checking site word credit usage and checking whether a word count has enough credits before translation.
- `online-programs-programs` ships the official Wix Online Programs Programs methods for creating, reading, updating, deleting, querying, searching, counting, bulk-updating, archiving, duplicating, ending, listing samples, and publishing programs. Writes are dry-run first; delete, archive, and end require `--ack-irreversible`.
- `online-programs-instructor-v2` ships the official Wix Online Programs Instructor V2 methods for creating, updating, querying, listing, assigning, changing, inviting, and unassigning instructors. Writes are dry-run first; invite, assignment changes, and unassign require `--ack-irreversible`.
- `b2b-site-transfer` ships the official Wix B2B Site Management Business Site Transfer V1 method for strategic partners. It uses account-level API-key auth, sends the target account as `wix-account-id`, and requires `--ack-irreversible` for live apply because it moves a site between accounts.
- `partner-profiles` ships the official Developer Preview Wix Partner Profile V1 methods for creating, updating, deleting, and reading partner profiles. Owner-facing commands use account-level API-key auth, public profile reads use no auth, and the official first-party-only contact method is not exposed.
- `viewer-cache` and `viewer-seo-tags` ship the official Wix Viewer Cache and SEO Tags methods. Cache invalidation is dry-run first and limited by Wix to developing sites using Web Methods or Router APIs; SEO tag resolution is read-only.
- GraphQL is docs-only/non-callable in this safe CLI because official Wix GraphQL accepts arbitrary queries and mutations against a unified schema. There is no generic `graphql` bridge command.
- Generic async job runner is docs-only/non-callable. Use the already shipped `async-jobs get` and `async-jobs list-items` read commands for official Async Job status and item reads.
- `site-folders delete` requires `--ack-irreversible`.
- `cookie-consent-policy` writes are plan-first. `delete-consent-config`, `bulk-delete-consent-configs`, and `bulk-update-consent-config-tags-by-filter` also require `--ack-irreversible`; `bulk-update-consent-configs` is Developer Preview in the official Wix docs.
- `dashboard-favorite-list` writes are plan-first. `update` requires the current `favoriteList.revision`, and `delete` plus `delete-favorite` require `--ack-irreversible`.
- `faq-category-v2` and `faq-question-entry-v2` writes are plan-first. `faq-category-v2 delete`, `faq-question-entry-v2 delete`, and `faq-question-entry-v2 bulk-delete` also require `--ack-irreversible`; update commands require current revisions; and `faq-question-entry-v2 set-labels` replaces all labels.
- `functions-v1` writes are plan-first. `functions-v1 update` requires the current `function.revision`; `functions-v1 delete` and `functions-v1 bulk-update-tags-by-filter` also require `--ack-irreversible` because delete is permanent and an empty filter can update all functions.
- `projects create-project` is now shipped in this boundary. It uses the account-level API-key auth family (`Authorization` + `wix-account-id`) and supports `--type WIX` only, with response-only success proof.
- `site-folders move-folders` supports up to 1,000 folder IDs per request and requires exactly one target form: `--target-folder-id` or `--to-root`.
- `site-folders move-sites` supports up to 500 site IDs per request and requires exactly one target form: `--target-folder-id` or `--to-root`.
- `site-folders` is API-key-only in the official Wix docs and is marked there as available to selected beta users.
- `site-actions bulk-delete` is the first shipped Site Actions command. It is intentionally narrow: up to 20 site IDs per request, dry-run first, `--apply --yes --ack-irreversible` for live apply, preflight site existence checks, and provider-response verification that every requested site moved to trash successfully.
- `site-actions duplicate` is now shipped. It uses the same account-level auth path as `site-actions bulk-delete` and `sites`, dry-runs first, requires `--apply --yes` (no `--ack-irreversible`), supports `--plan-out` and `--plan-in`, and requires provider `newSiteId` plus read-back verification of the new site. It currently ships incomplete copy behavior for some areas (`orders`, `contacts`, `invoices`, some 3rd-party app settings, domain, and Premium capabilities).
- `site-actions publish` is now shipped. It calls `POST /site-publisher/v1/site/publish`, returns `{}` on success, is dry-run first, requires `--apply --yes` (no `--ack-irreversible`), supports `--plan-out`, `--plan-in`, and `--receipt-out`, preflights by querying site existence with `sites query`, rejects stale plan drift, and verifies publish by re-querying the target site and checking `published=true`. If the site was already published before apply, the receipt `changed` field is `false`.
- Account Level Sites Skills is docs-only. Wix's `Query Sites` recipe maps to `sites query`; `Create Site from Template` is a multi-step recipe, so this CLI keeps the work on explicit commands such as `projects create-project`, `site-actions publish`, and `headless-oauth-apps create` instead of exposing `sites-skills`.
- `resellers` ships the official account-level package and product-instance methods: `get`, `query`, `create-package`, `adjust-product-instance`, `assign-product-instance`, `unassign-product-instance`, `update-package-external-id`, `cancel-package`, and `cancel-product-instance`. Writes are dry-run first, and cancel commands require `--ack-irreversible`.
- Nearby account-level team-member and invite APIs remain excluded. Official Wix docs say the `Users` and `Site Invites` families use a selected-beta account API-key path, so this boundary keeps them out until they can be covered honestly.
- CMS relationship writes are now available through dedicated commands: `data-items insert-reference`, `data-items remove-reference`, `data-items replace-references`. This is the intentional relationship write path in this boundary, separate from normal item write commands.
- `data-items replace-references` supports clearing all references by passing an empty reference-id array.
- CMS relationship write commands do not require `--ack-irreversible` for apply.
- `data-items save` is an upsert write and verifies by rereading the saved item ID returned by Wix.
- `data-items truncate` deletes every item in one collection, requires `--ack-irreversible`, verifies by count readback, and keeps no-useful-item-snapshot recovery limits explicit.
- `data-items bulk-remove` requires `--ack-irreversible`, verifies by item readback absence, and does not promise rollback.
- `data-items bulk-save` and `data-items bulk-update` are reviewed-plan writes. `bulk-save` refuses apply for items without explicit IDs unless `--return-entity` is enabled for safe verification.
- `data-items bulk-insert-references` and `data-items bulk-remove-references` are reviewed-plan writes verified through official `is-referenced` readback.
- CMS collection-schema write methods are now implemented as `data-collections create`, `data-collections update`, `data-collections patch`, `data-collections delete`, `data-collections create-field`, `data-collections update-field`, `data-collections patch-field`, `data-collections delete-field`, `data-collections add-plugin`, and `data-collections delete-plugin`. `data-collections patch` is intentionally narrow: it only supports `displayName`, `displayField`, and `permissions`. Field updates and plugin changes use the dedicated commands above. `data-collections delete-field` requires `--ack-irreversible`, can remove existing values from items across the collection, and `data-collections add-plugin` / `data-collections delete-plugin` can change collection behavior broadly.
